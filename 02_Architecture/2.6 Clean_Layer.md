# Clean Layer

## Purpose

The [data quality rules](2.5%20Data_Quality_Rules_and_Results.md) find what is wrong. The clean layer **repairs it**: it turns the raw source data into typed, standardized, de-duplicated tables that analytics, forecasting, and the AI agents can trust.

The guiding rule: **repair before discarding, and never guess.** A damaged value is recovered from the most reliable evidence available. A record is held back (quarantined) only when nothing can repair it, and a value that cannot be recovered stays empty and flagged.

Raw accuracy on transaction tables already looks high because most rows are fine. The full build (master data, ERP, business files, external data) takes about two minutes.

# How Values Are Repaired

In order of preference:

| # | Technique | Example |
|---|---|---|
| 1 | **Standardize the format** | `1r 0750` → `1R-0750`; `03/14/26`, `14-Mar-26`, `46095` (Excel serial) → `2026-03-14`; `'$1,234.50'` → `1234.50` |
| 2 | **Apply the Data Steward's reference data** | Approved product families, state codes, synonyms: `Paving` → `Road Construction`, `GET` → `Ground Engaging Tools`, `ISS` → `Goods Issue` |
| 3 | **Crosswalk duplicates to a surviving record** | `S103 Cat Parts Dist Ctr - Atlanta` → `S003`. Transactions keep their history and count toward the real supplier |
| 4 | **Survivorship** | The original record wins; a value it lacks is taken from its duplicate |
| 5 | **Cross-source reconciliation** | Recover the value from another document describing the same event (below) |
| 6 | **Infer from consistent related data** | A product's criticality from its category; a branch's region when every other branch in the state agrees |
| 7 | **Leave it empty and flagged** | 155 machines with no serial number are kept, serial unknown |

## Cross-source reconciliation

ERP documents describe the same events from several angles, so most damage can be **reversed exactly**:

| Damaged value | Recovered from |
|---|---|
| Sales line: missing branch or quantity, unknown part, future order date | The demand transaction for the same order line |
| Sales line: extended price wrong | Quantity × unit price |
| Demand: filled more than demanded | The identity *demanded = filled from stock + backordered + lost* |
| PO line: zero or negative quantity | Line value ÷ unit cost |
| PO line: wrong status, missing receipt date | Its goods receipts |
| PO line: unknown supplier | The part's primary supplier |
| Goods receipt: missing or impossible date | The inventory transaction it posted |
| Goods receipt: over-receipt | Accepted + rejected quantities |
| Goods receipt: PO number does not exist | **Orphan-receipt matching**: the one PO line with the same branch and part, last received that day, with at least that quantity. Recovered 192 of 215; the rest stay quarantined rather than being guessed |
| Inventory: negative balance | The running total of the transactions themselves |
| Part master: missing unit cost / invalid supplier | The part's latest purchase order / the supplier its POs actually go to |
| Supplier master: missing lead time | The promised dates on the supplier's own purchase orders |

## Interpreting spreadsheet layouts

The business files need their layout understood before their values can be cleaned:

| File | Layout problem | How it is read |
|---|---|---|
| Safety stock targets | Branch name only in the first row of each merged block; subtotal and blank rows; a second, older version of the file in circulation | Branch carried down to every row; `Total ...` and blank rows skipped; only the FINAL file is used |
| Inventory policy | A crosstab with a two-row merged header; `95%`, `93`, and `0.93` for the same kind of value; `2 wks` | Unpivoted to one row per category × criticality; percentages and weeks normalized |
| Supplier exceptions | Suppliers named in free text, never by ID; dates like `Q2 2025`; `DONE` / `Resolved` / `Open?` | Names normalized and matched against every known name variant, including duplicates; dates parsed; statuses mapped |
| Critical parts | **Priority exists only as red row fill**; two part numbers in one cell; retired parts below a text separator | Priority read from the stored fill colour; first part number taken; rows below the separator ignored |
| Forecast overrides (SharePoint) | `Richmond;#4` lookups; `0.4` / `40` / `+40%`; months with no year; people as claims logins | Branch name extracted; adjustments normalized to percent; the year inferred as the first such month after submission; logins matched to display names |

# Crosswalks

Every master entity has a crosswalk from each source ID (or name) to its surviving ID. Downstream code never joins on raw IDs.

| Crosswalk | Maps |
|---|---|
| `clean.branch_xref` | Branch IDs, duplicate IDs, case variants (`b001`), and branch names (`Richmond`) → branch ID |
| `clean.supplier_xref` | Every supplier ID, including the 10 duplicates → surviving supplier ID |
| `clean.part_xref` | Duplicate part IDs and superseded part numbers → current part |
| `clean.product_xref`, `clean.product_family_xref`, `clean.product_category_xref` | Duplicate and synonym records → surviving record |

# What Is Not Repaired, and Why

| Not repaired | Count | Why |
|---|---|---|
| Equipment serial numbers | 155 | No other source records them |
| Supplier tier where the stored value was wrong, not just badly formatted | 2 | `Tier-3` for a Tier 1 supplier looks valid once standardized |
| PO lines booked to a duplicate supplier ID | 302 | Mapped to the duplicate's real supplier, which is the correct business rule. The test data assigned these lines to duplicates at random, so some differ from the reference |
| Planning owner of one product family | 1 | No other source records it |
| Dates written as `Jun-24` or `Q1 2025` | 35 | The day was never recorded; the first of the month or quarter is used |
| Safety stocks entered as `TBD`, `see Jim`, or above the reorder point | 41 | The intended value is unknown; left empty |
| Service levels inherited from a policy cell typed as `95%` instead of 97% | 108 | The file's value is used; only the planner can correct the cell |
| Forecast overrides with a 10x typo (`400%`), no branch, or submitted twice | 24 | Held back for the planner to confirm |

## Performance notes

Two early versions took over 10 minutes; both fixes are general SQL Server lessons:

- **Never join on a function call.** `JOIN part ON part_number = fn_canon_part(x)` makes SQL Server evaluate the function for every pair of rows (hundreds of millions of calls). Computing the value once per row and storing it brought the ERP build from more than 10 minutes to 31 seconds.
- **Parse once, then aggregate.** Correlated subqueries that re-parsed 68,000 purchase orders for each of 4,400 parts were replaced by one parsed temp table and window functions (10+ minutes to 5 seconds).
