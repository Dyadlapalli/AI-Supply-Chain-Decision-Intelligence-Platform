# Data Quality Rules and Results

## Summary

The [Data Quality Strategy](2.2%20Data_Quality_Strategy.md) defined five dimensions of data quality. This document describes how they are implemented and how well they work.

**119 rules** check every raw source (master data, ERP, business Excel files, SharePoint, external APIs) in **26 seconds**. Because the source data was generated with a log of every defect planted in it, the rules can be scored like a test, not just run:

| Measure | Result |
|---|---|
| Planted defects (record level) | 16,625 |
| Found by the rules (**recall**) | 16,595 (**99.8%**) |
| Records flagged | 16,703 |
| Flags that were real planted defects (**precision**) | 16,691 (**99.9%**) |
| Real issues found that were **not** planted | 12 |

---

# How It Works

```text
raw tables ──► dq.chk_<rule> views ──► dq.usp_run_checks ──► dq.issue        (every failing record)
                                                        ──► dq.rule_result  (per rule: checked / failed)
                                                        ──► dq.run          (run history)
```

- **One SQL view per rule.** `dq.chk_M_SU_01` returns every duplicate supplier, with the record it duplicates. Any rule can be opened in SSMS to see exactly what it caught and why.
- **A rule catalogue** (`dq.rule_catalog`) records each rule's dimension, severity, and the **action** the clean layer takes:

| Action | Meaning | Example |
|---|---|---|
| `fix` | The clean layer corrects or standardizes the value; the record is kept | Part number `1r0750` becomes `1R-0750` |
| `quarantine` | The record cannot be trusted or repaired and is held back from analytics | A sales line for a part that does not exist |
| `flag` | The record is kept as is and reported to the Data Steward | A supplier marked inactive that purchase orders still use |

- **History is kept.** Every run is stored, so data quality can be trended over time (KPI DQ-01).

Files: rules in [`04_Database/dq/rules.sql`](../04_Database/dq/rules.sql), framework in [`04_Database/sql/05_dq_framework.sql`](../04_Database/sql/05_dq_framework.sql), runner [`04_Database/run_dq.py`](../04_Database/run_dq.py).

# What the Rules Missed (30 defects), and Why

Being clear about the limits is part of the result.

| Missed | Count | Why | What would catch it |
|---|---|---|---|
| Filled quantity increased but still below demanded | 14 | The value is wrong, but no rule can tell a 5 that should be 3 from a real 5 | Reconciliation against the inventory issue transactions (Step 3) |
| Synonyms: `Paving` vs `Road Construction`, `Hydraulic Excavators` vs `Excavators`, `Marine and O&G` | 4 | Same meaning, different words. Text normalization cannot match them | A reference list of approved values maintained by the Data Steward |
| Duplicate receipts whose date was also changed | 3 | The copy no longer matches the original on every field | Fuzzy matching within a date window |
| Layout-only issues (status meaning in a colour legend, rule in a footnote, retired items below a separator) | 3 | The information is in formatting, not in a value | Handled when the clean layer parses each file |
| Not real defects | 6 | The answer key logged a change that left the data valid: 4 all-digit part numbers "lower-cased" (no change), a policy minimum equal to (not above) its maximum, and a PO whose promised date equals its PO date | — (answer key overstated them) |

# Lessons Learned

Building the rules surfaced SQL Server behaviours that silently hide bad data. Each one would have made a rule look like it was working while missing defects:

1. **`=`, `GROUP BY`, and `LIKE` ignore trailing spaces in every collation**, even binary ones. `'Bridgestone OTR '` equals `'Bridgestone OTR'`. Padding must be detected with `DATALENGTH` and compared with a marker character appended.
2. **`[A-Z]` matches lower-case letters in a case-sensitive collation.** In `Latin1_General_CS_AS`, letters sort `a A b B ...`, so the range `A`–`Z` includes `b`–`z`. Pattern checks on letters must use a binary collation (`Latin1_General_BIN2`).
3. **`RULE` is a reserved word** and cannot name a table without brackets.

Scoring against the answer key also exposed defects in the **test data itself**: "defects" that left the value unchanged (lower-casing an all-digit part number) and an openpyxl call (`ws.cell(r, c, None)`) that silently does nothing. Both were fixed or filtered, so the scores above measure the rules, not the test data.
